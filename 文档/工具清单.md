# FieldOps 工具与节点清单（v1.0）

> 用途：对接外部系统时照着核对的那张表。三部分：**MCP 工具清单（6 Server / 24 工具）**、
> **Agent × 节点清单（4 Agent / 31 节点）**、**编排与容错**。
>
> 机器可读的工具定义（含 JSON Schema）见 [`文档/mcp_tools_schema.json`](mcp_tools_schema.json)，
> 由 `python scripts/dump_mcp_tools.py` 自动导出——工具改了重跑一次即可看到 diff。

### 1.7 作业流程（本服务-flow，写，需 Token）

| 工具 | 功能 | 参数 | 返回 | 对应 REST |
|---|---|---|---|---|
| `start_work_flow` | 启动作业流程会话 | `site_id`、`tenant_id`（必填）、`service_plan_id`、`initial_stage`、`discharge_order` | `session_id` / `current_stage` / `ai_message` | `POST /api/v1/work-flow/start` |
| `send_discharge_order` | 向已有会话下发退场工单（**只写检查点、不推进对话**，作业人员下次发言时生效） | `session_id`、`tenant_id`、`order`（dict，必填） | `found` / `status` / `message` | `POST /api/v1/work-flow/sessions/{sid}/discharge-order` |
| `get_work_flow_status` | 查会话阶段 / 轮数 / 状态 | `session_id`、`tenant_id` | `found` / `current_stage` / `total_turns` / `status` | `GET /api/v1/work-flow/active/{site_id}` |
| `get_work_flow_report` | 取服务/退场报告（流程 finished 时生成） | `session_id`、`tenant_id` | `found` / `report` / `stage_reached` / `total_turns` | `GET /api/v1/work-flow/{sid}/report` |
| `confirm_service_plan_item` | 护工确认某项服务任务执行完成（回写执行结果） | `plan_item_id`、`tenant_id`（必填）、`status`(done/missed)、`carer_name`、`actual_work_time` | `confirmed` / `status` | `POST /api/v1/work-flow/plan-items/{id}/confirm` |

> 服务计划相关的分工：**业务配置只读、执行结果可写**。外部系统能查服务项与等级可用项目、
> 能回报"谁在什么时候做了/没做"，但不能通过 MCP 增删改服务项目与频次——那属于业务侧职责。

### 1.8 鉴权与安全约定

- **只读工具免鉴权**、**写工具必须带 `Authorization: Bearer <MCP_ADMIN_TOKEN>`**；未配置 Token 时写工具一律 503（fail-closed）。
- 所有工具**必须传 `tenant_id`**：SQL 与 Milvus 查询强制按租户过滤，跨租户统一按"不存在"返回。
- 写工具额外做 **租户白名单**（`MCP_WRITE_TENANTS`）与**路径白名单**（`ingest_sop_document` 只能读 `data/` 目录）。
- 缓存联动：知识库导入/删除/重建后自动清理检索缓存，避免返回变更前的旧答案。

## 二、Agent × 节点清单

### 2.1 四个 Agent（共 31 个节点）

| Agent | 节点数 | 图结构 | 节点清单（按执行顺序） |
|---|---|---|---|
| 评估 Agent | 5 | 线性，无分支、无中断 | `parse_pdf` → `extract_structured` → `run_five_dimensions` → `diagnose_and_summarize` → `save_results` |
| SOP 问答 Agent | 11 | 条件分支（4 组条件边） | `quick_route`（入口快通道，含高危门控）→`quick_answer` ／ `classify_query` →（`hyde_generate` / `multi_query_rewrite`）→ `retrieve` →（`generate_rag` / `web_search` / `generate_direct` / `generate_general`）→ `save_memory` |
| 告警研判 Agent | 7 | 带中断点的线性流 | `run_four_tracks` → `aggregate_tracks` → `assess_risk` → `notify_supervisor` → `supervisor_review`【interrupt】→ `apply_supervisor_decision` → `dispatch_order` |
| 作业流程 Agent | 8 | 状态机 + 条件分支 | `load_context` →（计划缺失 → `notify_missing_plan` → END / 正常 → `check_stage` →（`generate_report` → `save_report` / `evaluate_response` → `generate_response` → `save_memory`）） |

### 2.2 节点与工具/数据源的对应关系

| Agent | 节点 | 依赖的工具或数据源 |
|---|---|---|
| 评估 | `parse_pdf` / `extract_structured` | PyMuPDF 解析（线程池）、结构化提取 LLM |
| 评估 | `run_five_dimensions` | 5 次并行 LLM 调用（`asyncio.gather`），权重 0.30/0.25/0.20/0.15/0.10 |
| 评估 | `diagnose_and_summarize` | 结构化输出 LLM、优先级排序 + 风险等级建议 |
| 评估 | `save_results` | `repositories.save_assessment_result` |
| SOP 问答 | `classify_query` / `hyde_generate` / `multi_query_rewrite` | 意图与改写 LLM（意图结果走 Redis 缓存） |
| SOP 问答 | `quick_route` / `quick_answer` | `core/quick_index.py`：术语规范化 + BM25 + 高危门控 + 覆盖率/主题/分差三重门控；命中直接返回 SOP 原文（不调模型、不查库），高危问法强制回落慢链路 |
| SOP 问答 | `retrieve` | BGE-M3 稠密+稀疏编码 → Milvus 混合检索 → WeightedRanker → BGE-Reranker 精排（Top-10 → Top-3）；命中 Redis 缓存则直接返回 |
| SOP 问答 | `web_search` | 联网搜索（Tavily → DuckDuckGo） |
| SOP 问答 | `generate_rag` / `generate_direct` / `generate_general` | 生成 LLM（带引用） |
| 告警 | `run_four_tracks` | `iot_repo` + `repositories.get_latest_assessment`：前三轨查库、第四轨取最近一次风险评估（缺失按无记录继续） |
| 告警 | `assess_risk` | 结构化输出 LLM（失败降级为默认中风险） |
| 告警 | `notify_supervisor` | `repositories.save_alert_triggered`（落库四轨 + 风险评估） |
| 告警 | `supervisor_review` | `interrupt()` 暂停 + checkpointer 持久化状态 |
| 告警 | `apply_supervisor_decision` / `dispatch_order` | 决策合并 + 工单 LLM 生成 + `repositories.save_alert_dispatched` |
| 作业流程 | `load_context` / `notify_missing_plan` / `check_stage` | `service_plan` / `service_history`（来自 `ServicePlanProvider`：本地库或业务系统；取不到时标记 `service_plan_missing` 并如实告知，不再用 mock 计划兜底）+ 阶段轮数上下限（`STAGE_MAX_TURNS` / `STAGE_MIN_TURNS`）+ `state.discharge_order`（业务系统 退场工单，`/start` 或每轮 `/chat` 注入：收到后当前阶段达 min 即收敛到 复评 → 退场评估 主干道，无工单则复评后回日常巡检开新循环） |
| 作业流程 | `evaluate_response` / `generate_response` | 评估与生成 LLM |
| 作业流程 | `generate_report` / `save_report` | 报告生成 LLM + `repositories.save_work_flow_report` |

## 三、编排与容错

| 能力 | 实现 |
|---|---|
| 意图路由 | `classify_intent`（LLM 结构化分类）→ 单智能体（SINGLE）/ 流水线（PIPELINE）/ 澄清（CLARIFY）三模式；失败降级关键词匹配，再兜底 SOP 问答 |
| 流水线 | `care_workflow = 评估 → 作业流程`，评估结论自动转成 `service_plan`（风险等级 + 任务清单）注入下游 |
| 超时分级 | 评估 300s、作业流程 180s、告警 120s、SOP 问答 120s（`_AGENT_TIMEOUT`） |
| 三层容错 | `with_retry`：重试 → 降级（如告警返回"需人工核实"）→ 系统兜底；结果里用 `fallback_used` 标记 |
| 记忆 | checkpointer 落 PostgreSQL（`AsyncPostgresSaver`，`thread_id = site_id + session_id`，同 thread 下按 `checkpoint_ns = agent_type` 隔离）；窗口裁剪只留最近 10 轮进 prompt；摘要每新增 10 轮压一次并写回 `existing_summary`（随检查点持久化）；连不上库可回落内存 |
| 断点清理 | `DELETE /api/v1/chat/session/{site_id}/{session_id}` → `adelete_thread`（整线程原子删除，仅 admin / 仅本租户点位）；**只手动触发**，无 TTL 与定时任务，条件：周期结束 + 审计期已过 + 无待确认告警 |
| 缓存 | 意图识别 TTL 600s、SOP 检索 TTL 300s；fail-open；知识库变更即失效（实测同问检索 2.01s → 0.008s） |

## 四、怎么保持这份清单不过期

1. 改了 MCP 工具（增删参数、改描述）→ 重启后端 → `python scripts/dump_mcp_tools.py` 重新导出 schema；
2. 改了 Agent 节点 → 更新本文件第二节，并核对节点总数（当前 5 + 11 + 7 + 8 = 31）；
3. 对外交付或联调前，把第一节的表和 `文档/mcp_tools_schema.json` 各扫一遍，确保文档字段与代码一致。
